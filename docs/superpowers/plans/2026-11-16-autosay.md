# Autosay Implementation Plan

> **For agentic workers:** Use the available `executing-plans` skill to implement this plan task by task. Independent plan review precedes implementation; finished-change review precedes landing. This document authorizes neither execution nor a daily-runtime installation by itself.

**Goal:** Offer one editable next-user-message suggestion in every supported BB agent thread, independent of its working-agent provider.

**Architecture:** Autosay owns context selection, model invocation, instructions and cancellation. BB owns the transient suggestion state and acceptance into its existing draft; the shipped Composer plugin renders that state and routes keyboard/touch acceptance through the same host operation. The generator is independent of the working agent.

**Tech Stack:** Existing BB TypeScript/React/TipTap monorepo, Plugin SDK, Zod, Vitest and an explicit OpenAI-compatible Chat Completions connection. No new platform, agent thread, database or daemon protocol.

## Proposed contracts and ownership

These are new API designs, not existing SDK symbols. Prefix every public addition with `experimental_`, register it in `docs/api_to_audit.md` and Plugin Guide inventory.

```ts
type SuggestionSnapshot = {
  composerKey: string;
  threadId: string;
  contextRevision: string;
  draftRevision: number;
};
type SuggestionCandidate = {
  requestId: string;
  snapshot: SuggestionSnapshot;
  text: string;
};
type GenerationResult =
  | { kind: 'suggestion'; text: string }
  | { kind: 'none' };
type AcceptResult = 'accepted' | 'stale' | 'ineligible';
```

Host exposes an experimental scoped suggestion controller with reactive eligibility/snapshot, `show(candidate): boolean`, `clear(requestId): void`, `accept(requestId): AcceptResult` and a lifecycle observer for shown/accepted/dismissed. It owns an increasing draft revision even for type-then-delete. Candidate state is memory-only and is never part of draft serialization, history, autosave, clipboard or submit payload. Clear is request-scoped so old cleanup cannot clear a newer candidate.

Eligibility requires a mounted, visible thread composer in the focused pane and foreground document, known idle/completed context, a live connection, empty draft including mentions/attachments/uploads, no queued work about to run, no input lock/voice, and no open question/approval. Capability absence in a custom composer yields unsupported/off, not a DOM overlay fallback. Renderer advertises suggestion support through the editor bridge; built-in Composer supports it.

Context revision is a tuple of the latest conversation/turn source identity, context-clear boundary, thread lifecycle and open-question identity/revision. Do not use text hashes or timeline sequence alone: question state can change independently. Host invalidates on locally received changes, disconnect, scope/focus change, edits, disable and disposal. This does not promise awareness of an unseen remote event before delivery; the normal send/permission path remains authoritative.

`accept` synchronously compares the entire captured snapshot against current host state and rechecks eligibility before the existing draft replacement. Keyboard and touch call that same function. Tab is consumed only for an actually accepted eligible candidate, without modifiers, repeat, IME or a higher-priority menu. Otherwise the current keyboard path runs unchanged. Escape cancels both visible and pending requests.
