# Intake design

## Custody and records

Use one thread_send_intakes table. A row stores server/native-compatible identity, optional real client submission UUID, per-thread intake_order, immutable original envelope fingerprint, editable current envelope, revision, state, claim token/epoch/lease, truthful admission/native receipts, stable clear/compact correlations, bounded effect checkpoints and failure. Thread deletion cascades. Unique thread/client identity and thread/order indexes protect replay and monotonic order. Allocate MAX(order)+1 inside an immediate SQLite transaction; retain terminal key/hash/receipt/order anchors and compact payload after terminal/native handoff. No undelivered TTL expiry.

Same-project ready attachment ownership is acquired through the existing helper in the admission transaction. Cross-project/uninventoried requests reserve unacknowledged staging order before asynchronous copy/inventory; only then atomically pin target bytes and finalise admission. Persist resolved target references without changing original replay fingerprint or requested mode. Host paths remain path references. Staging validation failure is rejected without an accepted receipt.

## Shared lane and native handoff

All participating modern, legacy and no-ID send ingress uses the same per-thread lane. No-ID requests receive only a server request identity; their original absence of clientSubmissionId reaches the native pipeline. Old clients wait for truthful sent/queued receipts. Negotiated requests with a real client ID receive accepted after the custody transaction. No resolved execution tuple is fabricated.

The worker enters the original inline pipeline in intake_order, preserving mode, field presence, compactFirst, origin/sender/plugin/service-turn, hook attempt/queuedMessages/initiator and mention context. Serial preparation ends at committed native queue/request/start custody or standalone clear completion. afterCommit wakes the next row immediately; HTTP/provider continuation cannot hold the lane. compactFirst's compact checkpoint alone does not release the parent: the following original message must hand off. Native sortKey, scheduling, steer and reorder policy governs after handoff; intake order is not provider FIFO.

## Claims, effects and recovery

Claims use token/epoch CAS and bounded leases. Startup scans all thread statuses in bounded batches, with event-driven wakes and finite lease timers. Stale workers must fail within each committing transaction. Seal before first visible/irreversible effect, including effectful hooks. Pre-seal revision CAS permits edit/cancel; after seal 409 means the action did not occur and custody remains. Failed acknowledged heads block later preparation. Unsealed failures permit explicit revisioned retry/cancel; sealed uncertainty permits only server-evaluated reconciliation from committed native evidence. Never silently skip or blindly repeat external effects.

Six narrow seams: requested append and prompt history transaction; native queue insertion transaction; pending-thread first-start/provision custody transaction; standalone clear's stable operation and actual completion-event transaction; compact's stable request and correlated sub-request checkpoint without releasing parent; recovered model override mutation transaction after catalog await. Narrow internal authority connects these seams; no daemon wire change. Checkpoints cannot promise exactly-once plugin or provider effects.

Same real client ID and canonical original fingerprint replays its retained receipt; changed original conflicts. Edits preserve immutable original hash. Native transfer retains qsub_<normalised UUID>. Read/action revisions describe current custody; post-seal conflicts retain rows/content. Queue send-now/reorder before genuine native handoff is explicitly not ready.

B must integrate joint queue/timeline/snapshot/push observation before overlay retirement; an accepted receipt alone cannot retire local custody. Preserve M1 causal handoff, M2 Web Lock exits, identity fences, all IDs/group-zero continuation and confirmed-cancel [0,1,0]. C must inspect actual DB/WAL offline with writers stopped before every managed incompatible manual/automatic/Desktop pointer rollback. Nonterminal custody refuses rollback. ## Exact additive server contract (A implementation choice)

POST /threads/:id/send remains typed as the existing SendMessageRequest -> SendMessageResponse and now enters the same intake lane as modern admission. POST /threads/:id/send-admission takes the same original envelope plus required admissionVersion:1 and clientSubmissionId; it returns only the typed accepted receipt. GET /threads/:id/send-intakes advertises admissionVersion:1 and returns a bounded page of canonical rows, including retained terminal/native handoff evidence and nextAfterOrder. POST /threads/:id/send-intakes/action applies revision CAS edit/cancel/retry/reconcile; send-now/reorder explicitly conflict before native handoff. Existing native actions remain authoritative after transfer.

The additive admission entrypoint replaces the earlier proposed optional negotiation on the existing send route. Reason: keeping the existing route's strict sent|queued response type truthful lets Subpart A remain separate from B; widening that response type would immediately force SDK/UI/CLI consumers into B. This is an additive negotiated entrypoint, not a replacement route or a fake legacy adapter. Both routes share service, identity/hash replay, original-envelope worker and transaction checkpoints. Same authenticated plugin service-turn authorisation runs before either route admits. Same-reviewer contract delta must cover the choice. No client enablement is claimed by A alone.

Participating ingress is the existing-thread send route, the additive admission route and legacy deferred-message replay through acceptThreadSendRequest. Thread creation, native queue drain/retry and the dedicated compact/clear-context action routes retain their native entrypoints. Command input sent through either send route participates in the intake lane; dedicated context actions are not converted into synthetic message envelopes. This scope does not establish a total order between a pending intake and an independently invoked dedicated context action. Addenda13/14 accept this boundary with explicit documentation and regressions: like native queued messages, an admitted send still in preparation can execute after an independently completed clear. Native queue drain may proceed while pure intake preparation is held, preserving native row/group order. The existing per-thread context guard still arbitrates real send/clear effects. This does not turn dedicated actions, native drain or thread creation into lane participants. Three real SQLite/HTTP context boundary regressions passed in the full server run; packaged provider concurrency remains unverified. See verification.md.

Before a new identified intake acknowledges custody, native queue identities and stored requested-event submission identities are checked. The targeted historical check has no last-1000-event cutoff and treats UUID casing canonically. It uses existing queue/event storage without a new index or identity table. Retained intake identity/hash replay remains authoritative after handoff. This source implementation still requires runtime and query-cost verification.

Cross-project copies use a deterministic private target path intake-<intake id>/<source project>/<original path> through the existing inventory/copy mechanism. This prevents a same-name target asset from substituting different source bytes. A ready private target can finish an unacknowledged staging recovery after source deletion without rereading source bytes; incomplete staging targets remain unacknowledged failures. The admitted current envelope stores the target references, while the original fingerprint/envelope remains immutable until payload compaction. Attachment inventory/final-rename writes receive the same local transaction authority check after asynchronous I/O. This adds no asset table or daemon field.

## Addenda13/14 recovery contract

The reviewer withdrew the earlier failed-head-release suggestion after reconciling the current approved B3/B4. A failed head retains custody and blocks following checkpoint entry. `reconcile` on the existing action endpoint requires the exact failed, sealed revision. One immediate transaction reads authoritative native storage and either transfers the same row with its genuine native receipt, or increments its revision while retaining failed custody, content and an unresolved error. The action never executes/resends, invents an identity or accepts a client's claim of delivery.

Evidence is an actual native queue row with the original queue identity and owning thread, a stored original-identity requested event at the native request handoff seam, a correlated first-start requested event plus matching committed native startup context/provider acceptance, or a completed clear event with the stored operation ID. A standalone compact can use its stored compact request ID. A compactFirst parent's compact checkpoint/subrequest cannot settle the following original message. Mere intake/start intent, thread status or a failed effect's existence is not evidence. A no-ID row lacking an exact stored native correlation remains unresolved. External hook/mention/model effects alone cannot prove native custody or justify a resend.

Effect metadata uses the reserved `_intakeEffectStage` field in this table's currentEnvelope JSON. Values are hook, mention, model, clear, compact, startup-cleanup or request. The field is removed before native envelope validation; immutable original envelope/hash is unchanged. Canonical rows expose the typed nullable effectStage. No SQL, generated snapshot or additional storage entity is introduced for recovery. Terminal payload compaction also removes this stage; retained nativeHandoff/nativeReceipt supplies the final evidence.

Pure attachment, catalog and execution preparation does not seal. Before effectful hook invocation (inside its existing evaluation lock), mention resolution, model mutation or startup cleanup, a lazy existing per-thread send guard is acquired before sealing. Standalone clear acquires its own exclusive guard before its seal/stop. Requested/history, queue and first-start handoff fences remain atomic with native custody; compact checkpoint remains atomic without releasing its parent. Release/stop/commit cleans up the lazy guard idempotently. A stale worker cannot turn a late grant into an effect after its claim is revoked.

A proven unsealed deterministic ApiError 4xx (excluding 408/429), or attachment validation error, becomes terminal rejected with the original status/body encoded as a discriminated stored outcome in nativeReceipt. Legacy replay returns that same error; it never fabricates a successful native receipt. Identity/hash/order/admission anchors remain, payload compacts, and the next row may enter. An error after seal stays failed even if its HTTP status is 4xx. A known original 4xx is stored as an error outcome on that failed row; originating legacy callers and same-ID replay retain its status/code/message with retained-custody/recovery details. This outcome is not a terminal rejection or native handoff proof.

A typed pre-seal context-guard collision returns the claim to pending. A one-shot guard-available wake and finite 10s fallback resume it, with at most 3 automatic retries (claim epochs 1–4); exhaustion retains unsealed failed custody for explicit retry/cancel. New arrivals cannot bypass a registered guard wait. Stop removes listeners/timers. This is bounded recovery, not polling or automatic ambiguous-effect replay.

Legacy followers receive 409 intake_blocked immediately behind a failed head; existing followers settle when the head fails. The failed head replays its known original 4xx with custodyRetained:true and recoveryRequired:true, or reports intake_blocked when its original result is unknown. A 30s legacy wait bound also reports retained custody when preparation is still held. Error details contain actual intakeId/blockerId and custodyRetained:true. A legacy timeout is not cancellation or absence of custody; old clients still receive only genuine sent/queued receipts on success. Negotiated accepted is the retained historical admission checkpoint, not a claim that its original pending revision is the current row state. Canonical reads/actions supply the current revision/state.

Production startup keeps the worker unready until actual startServerPlugins settlement (success or logged startup failure), then explicitly starts recovery. The provider registry readiness API has a 30s timeout and cannot authorise this transition. Early HTTP admission may acquire custody, but cannot claim/dispatch before that explicit startup signal. Permanent shutdown closes this signal before teardown, so a late plugin-startup completion cannot reopen it. Server move stops workers before its stop-work/snapshot boundary and resumes only through the native unfreeze path. No readiness polling is added.


## Legacy checkpoint and inline-result semantics

The custody checkpoint releases the intake lane and publishes its canonical admission/handoff. A legacy waiter for a currently executing inline attempt still awaits that original attempt's result, preserving its native receipt and command-queue timing. It does not hold later intake preparation after committed handoff. Server-only no-ID receipts retain the old sent/queued shape; internal request identity remains in nativeHandoff rather than appearing as a new requested receipt field. Recovery uses the same identity-dependent receipt rule. Initial event-driven worker wakes use a microtask; lease expiry, attempt bounds and guard backoff remain finite timers.

Exact same-ID/same-envelope replay returns the retained original receipt; changed-envelope replay conflicts without another native effect. This supersedes the overlay-only test's former expectation of rejecting every retained repeat. Queue/group/order assertions remain required. Selected runtime corrections passed, including active-inline stop/restart/replay. Full runtime acceptance remains partial because the full-run scrollback anomaly is unresolved and standalone build is missing; see verification.md.
