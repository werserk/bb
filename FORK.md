# werserk/bb fork

This is a maintained downstream fork of [get-bb/bb](https://github.com/get-bb/bb). `fork/main` starts at the upstream release tag `desktop-v0.48.1` and adds only downstream patches; it integrates upstream `desktop-v*` release tags, never upstream `main`. Architecture, branch model, release policy and the patch ledger live in the maintainer's repository: `docs/bb-fork/` in [werserk/bb-plugin-lab](https://github.com/werserk/bb-plugin-lab) (private).

The provider-independent visible plan tool lives in `apps/server/src/services/threads/thread-plan-tool.ts`: runtime configuration contributes `bb_update_plan` to every provider, and the authenticated tool-call route writes normalized `planSteps` into the existing timeline. The latest snapshot remains available after turn completion (including idle and error) until a new snapshot replaces it or an empty plan clears it. A context clear also hides a plan from before that boundary; the explicit includeClearedContextHistory view can still read it. Fully completed plans remain visible so the result of the last task stays inspectable; a new turn alone does not imply a new task. Optional single-line step `note` (1–1000 trimmed characters) and `actor` (1–100) round-trip through the same timeline JSON and pendingTodos response; legacy native plans omit them. This additive event-payload extension was owner-approved for item 1b; it rewrites no old events and adds no DB table, migration, or parallel store. The existing head-state query selects the latest plan through the partial plan index with LIMIT 1, even outside the visible page. The app consumes this response, not a timeline scan per render. Item 1c can move ThreadTodoCard using the existing pendingTodos, disclosure state and optional note/actor fields; it must retain the empty-plan clear behavior.

Follow-up: native provider steps with status `failed` still map to completed in the todo card (pre-existing behavior). A separate status/UI change should distinguish failure without counting it as successful completion. Item 1c owns any staleness cue for a retained plan; no cue is added by 1b.
